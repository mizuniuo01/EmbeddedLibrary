# EmbeddedLibrary S1～S8 使用与设计复核计划

## 1. 复核目标

本计划用于复核 S1～S8 已完成组件的实际使用方式和设计边界。重点不是重复代码风格审核，而是确认调用方能否明确回答以下问题：

- 组件属于哪一层，允许依赖哪些模块；
- 调用方需要分配哪些对象、数组、缓存和 `context`；
- 每项资源由谁拥有，何时创建，何时失效；
- 如何初始化、调用、查询、复位、重新初始化或停止使用；
- 内部状态如何变化，数据如何流动；
- 裸机主循环、普通任务、ISR、DMA 和 FreeRTOS 中的使用边界；
- 错误如何返回、记录、恢复和向上层传递；
- 哪些行为由组件保证，哪些行为必须由调用方保证；
- 当前设计是否符合个人工程的实际使用需求。

本阶段只梳理文档、确认设计和记录问题，不直接修改生产代码。发现问题后先讨论，确认修复方案后再单独开启修复动作。

## 2. 复核范围和顺序

复核按依赖顺序逐阶段推进，每次只处理一个阶段；当前阶段完成梳理并由用户确认后，才进入下一阶段。

| 顺序 | 阶段 | 组件 | 当前状态 | 主要依赖关系 |
| --- | --- | --- | --- | --- |
| 1 | S1 | `scheduler` | 待修复 | 裸机主循环提供时间和任务回调 |
| 2 | S2 | `mizu_fifo` | 待修复 | 上层 owner 模块提供私有对象、字节存储和同步边界 |
| 3 | S3 | `mizu_pid` | 已确认 | 平台无关控制计算 |
| 4 | S4 | `mizu_cascaded_pid` | 已确认 | 内部拥有两个 `mizu_pid` |
| 5 | S5 | `mizu_parameter_service` | 待修复 | 为菜单提供参数描述和读写能力 |
| 6 | S6 | `mizu_command_service` | 待修复 | 为菜单提供命令描述和执行能力 |
| 7 | S7 | `mizu_status_service` | 待修复 | 保存上层显式上报的当前状态 |
| 8 | S8 | `mizu_menu` | 待修复 | 编排 parameter、command 和项目适配器 |

## 3. 统一梳理模板

每个阶段复核时，更新对应的 `docs/components/*.md`，按以下结构补充内容：

1. 组件定位与架构层级；
2. 允许依赖和禁止依赖；
3. 调用方资源清单；
4. 对象、数组、缓存和 `context` 的所有权；
5. 资源分配方式和生命周期；
6. 装配阶段初始化步骤；
7. 最小可用调用示例；
8. 正常运行调用时序；
9. 内部状态和数据流；
10. 重初始化、复位、销毁和重新绑定语义；
11. 执行上下文、阻塞性、并发和重入限制；
12. ISR、DMA、裸机和 FreeRTOS 边界；
13. 错误结果、部分成功和恢复方式；
14. 调用方保证事项；
15. 组件自身保证事项；
16. 需要用户确认的设计问题；
17. 现有测试、验证证据和未验证边界。

每个阶段同时在本文件更新状态和复核摘要。组件说明负责具体使用方式，本文件负责复核进度、问题编号和确认结论。

## 4. 复核中需要区分的内容

每个结论必须标记为以下一种类型：

- **代码事实**：可由当前 `.c/.h` 和测试直接确认的行为；
- **文档约定**：当前组件说明中已经声明的使用规则；
- **待确认设计**：代码允许多种解释，需要用户选择；
- **已确认设计**：用户已经明确接受的行为；
- **待修复问题**：已确认不符合要求，需要后续单独制定修复方案。

不能因为代码已经实现，就默认实现行为等于最终设计意图。

## 5. 阶段交付流程

每个阶段按以下顺序执行：

1. 阅读实际公共头文件、实现、组件说明和现有测试；
2. 在对应组件说明中补充资源、生命周期、调用时序和内部状态；
3. 在本文件将阶段状态改为“梳理中”；
4. 向用户说明完整使用流程和关键设计选择；
5. 列出必须由用户确认的问题；
6. 等用户确认并记录结论；
7. 若发现问题，只记录问题和建议，不直接修改生产代码；
8. 用户确认该阶段完成后，将状态改为“已确认”或“待修复”；
9. 用户手动开启下一阶段后再继续复核。

## 6. 各阶段复核重点

### S1：scheduler

- 调度器对象、任务配置表、运行槽数组和任务 `context` 的分配与生命周期；
- `init → update → run → get_stats` 的调用链；
- tick 基准、回绕、异常大间隔和重新基准；
- ready、elapsed、missed、运行统计和错误统计的状态变化；
- 优先级排序、任务 ID、回调错误隔离和每轮最多执行一次；
- 空任务表和重新初始化语义。

### S2：mizu_fifo

- FIFO 对象和 storage 的分配位置、实际容量和保留空槽；
- 初始化一次后的对象、storage 和数据缓冲区生命周期；
- 写入、读取、单字节包装、零长度、满、空和部分操作语义；
- 单生产者/单消费者约束、原子性、内存可见性和同步边界；
- storage 与对象、输入缓冲区、输出缓冲区的重叠约束；
- FIFO 与帧解析、串口/DMA 适配的职责边界。

### S3：mizu_pid

- PID 对象和配置的分配、配置复制与动态状态；
- `init/reset/calculate` 生命周期；
- 积分、微分历史、输出状态、显式 `dt` 和限幅；
- 条件积分与 back-calculation 的选择和边界；
- 输入输出重叠、失败事务性、重初始化和并发限制。

### S4：mizu_cascaded_pid

- 串级对象内部两个 PID 的所有权；
- 外环、内环配置和动态历史的替换与复位；
- 外环输出到内环目标的传递、共享 `dt` 和级间边界；
- 局部副本计算、失败回滚和输出提交；
- 与航向、差速、电机和项目控制语义的边界。

### S5：mizu_parameter_service

- 分组表、描述符、字符串、getter/setter 和 `context` 的所有权；
- 注册表初始化、ID 唯一性、范围、步长和当前值校验；
- `get/set/adjust`、纯变换函数和菜单借用描述符；
- 可写/只读、bool、浮点精度、步长缩放和错误传播；
- 注册表不可变约束以及 callback context 生命周期。

### S6：mizu_command_service

- 分组、描述符、handler 和 `context` 的所有权；
- 初始化和 ID 唯一性；
- 同步执行、BUSY、错误状态和最近快照；
- handler 的阻塞、重入和并发限制；
- command 与业务动作、异步动作、菜单和 RTOS 任务的边界。

### S7：mizu_status_service

- 状态服务对象和记录数组的分配与生命周期；
- source ID、空槽、重复上报、容量耗尽和 clear 复用；
- report、clear、count、query 的调用顺序；
- 当前状态而非历史记录的职责边界；
- 下层错误返回、上层显式上报、显示/通信/日志读取边界；
- ISR、任务和同步限制。

### S8：mizu_menu

- menu 对象、根项目、分组、条目、展示页、步长缓存和服务依赖的所有权；
- Composition Root/Domain 的装配方式；
- 初始化失败事务性和运行期固定注册表；
- 根列表、分组、参数编辑、步长编辑、命令确认、展示页状态机；
- 输入事件适配器和输出语义视图适配器；
- 参数草稿、冲突检测、提交、取消和 feedback；
- command 执行、BUSY、错误反馈和非阻塞处理；
- `process()` 时间语义以及 `query_view()` 容量、预检和 getter 错误语义；
- menu 与 parameter/command 的横向编排例外。

## 7. 问题记录格式

问题编号采用 `REVIEW-S<阶段>-<序号>`，每项包含：

- 所属阶段和文件；
- 代码事实；
- 对调用方、资源生命周期或架构的影响；
- 当前是实现问题还是设计选择；
- 用户确认结论；
- 后续修复方案和验证结果。

问题不得通过修改代码后再反推设计结论。修复必须在用户确认方案后作为独立动作执行。

### REVIEW-S1-001：scheduler 的一次初始化契约尚未落实

- **阶段和文件**：S1，`services/scheduler/scheduler.c` 的 `scheduler_init()`。
- **代码事实**：当前实现会在校验前将 `scheduler->initialized` 置为 `false`，并允许后续成功初始化覆盖已运行实例。
- **已确认设计**：scheduler 实例只允许一次成功初始化。对已初始化实例再次调用 `scheduler_init()` 必须返回 `MIZU_STATUS_INVALID_STATE`，不得改动旧实例、配置表绑定、运行槽或统计。首次初始化失败后实例保持不可用。
- **影响**：当前误调用第二次初始化，或在已运行实例上以非法参数尝试初始化，会破坏旧调度器的可用性。
- **后续动作**：S1 使用与设计复核结束后，单独制定生产代码修复和回归验证计划。

### REVIEW-S2-001：mizu_fifo 的一次初始化契约尚未落实

- **阶段和文件**：S2，`libraries/mizu_fifo/mizu_fifo.c` 的 `mizu_fifo_init()`。
- **代码事实**：当前实现允许对已初始化对象再次调用 `mizu_fifo_init()`，并直接替换 storage、容量和游标状态。
- **已确认设计**：FIFO 对象只允许一次成功初始化；对已初始化对象再次调用必须返回 `MIZU_STATUS_INVALID_STATE`，不得修改旧对象、storage 绑定或游标。首次初始化失败后对象保持未初始化状态。
- **影响**：误调用重复初始化会丢失未读数据，并可能把 FIFO 绑定到错误的 storage。
- **后续动作**：S2 使用与设计复核结束后，单独制定生产代码修复和回归验证计划。

### S3：mizu_pid 已确认

- PID 对象和配置由调用方静态或长期存活对象持有，组件不分配动态内存；初始化时复制配置，不保存配置指针。
- `mizu_pid_init()` 保留可重复初始化语义，成功后替换配置并清除动态历史；调用方应由 owner 统一构造新配置，在安全边界一次性切换，不通过逐字段修改运行中对象来改变控制参数。
- `mizu_pid_reset()` 只清积分、输出和微分历史，不修改配置。
- `mizu_pid_calculate()` 每次接收调用方提供的 setpoint、measurement 和 `dt`；时间来源、单位一致性和调用周期由调用方保证。
- 在线调参时，Parameter/菜单等适配层的 setter 必须在返回成功前把新配置应用到正在运行的 PID 实例；getter 读取已生效的控制配置，不能只更新显示用副本。
- 配置应用失败时，权威配置、活动 PID 实例和对外显示值必须保持一致的旧状态；显示值不得先于控制器实际生效。
- 输出缓冲区与 PID 对象的重叠由调用方保证，PID 不做地址范围检测。
- 非有限输入、非法 `dt` 或中间溢出只通过状态返回；是否停机、降级、记录或进入安全状态由 Application/Domain 决定，PID 不自动锁定故障。
- 未发现需要登记的 S3 实现问题。

### S4：mizu_cascaded_pid 已确认

- 串级对象内部拥有外环和内环两个 `mizu_pid_t`；调用方只拥有串级对象并提供两级配置。
- 外环最终输出直接作为内环目标，不增加通用级间限幅；两级使用同一个 `dt`。
- 公共接口只返回内环最终输出，不额外返回外环输出、内环目标或诊断快照；需要诊断时由 Domain/Application 自己组合。
- 配置更新沿用 S3：构造完整新配置后通过 `mizu_cascaded_pid_init()` 应用，成功后两级动态历史清零；在线调参的连续性、无扰切换和实验重启由 Domain/Application 决定。
- 外环和内环的业务含义由 Domain 决定，串级库不绑定位置、角度、速度、电机或项目模式语义。
- 计算和 reset 使用局部副本事务提交，任一级失败时原对象和输出保持不变。
- 未发现需要登记的 S4 实现问题。

### REVIEW-S5-001：parameter service 的一次初始化契约尚未落实

- **阶段和文件**：S5，`services/parameter/parameter.c` 的 `mizu_parameter_service_init()`。
- **代码事实**：当前实现允许对已初始化 service 再次调用 init，并替换注册表指针、分组数量和参数数量。
- **已确认设计**：参数服务只允许一次成功初始化；已初始化对象再次 init 必须返回 `MIZU_STATUS_INVALID_STATE`，不得修改旧注册表或服务状态。首次初始化失败后服务保持未初始化状态。
- **影响**：运行期误调用重复初始化可能让菜单、通信或其他调用方看到另一套注册表，破坏稳定 ID 和描述符生命周期。
- **后续动作**：S5 使用与设计复核结束后，单独制定生产代码修复和回归验证计划。

### S5：mizu_parameter_service 已确认

- parameter service 只保存静态注册表和回调绑定，不持有业务参数当前值副本。
- getter 每次直接读取 owner 的已生效配置；getter 必须轻量、同步、非阻塞。实时传感器/监测数据不注册为 parameter。
- setter 成功返回前必须已经把新值应用到真实业务对象或活动控制器；只修改显示副本不算成功。
- parameter service 只做单参数类型、范围、步长和权限路由；跨字段整体校验/事务只在 owner 存在实际业务关联约束时使用，不作为通用强制流程。
- 并发一致性由 owner 和调用上下文保证；service 只支持串行调用，不提供缓存、锁或 ISR 安全。
- 未发现除 `REVIEW-S5-001` 外的 S5 实现问题。

### REVIEW-S6-001：command service 的一次初始化契约尚未落实

- **阶段和文件**：S6，`services/command/command.c` 的 `mizu_command_service_init()`。
- **代码事实**：当前实现允许对已初始化 command service 再次调用 init，并替换命令注册表和最近快照。
- **已确认设计**：command service 只允许一次成功初始化；已初始化对象再次 init 必须返回 `MIZU_STATUS_INVALID_STATE`，不得修改旧命令表、快照或服务状态。首次初始化失败后服务保持未初始化状态。
- **影响**：运行期重复初始化可能替换稳定命令 ID 和 handler 绑定，使菜单或其他入口执行到不同动作。
- **后续动作**：S6 使用与设计复核结束后，单独制定生产代码修复和回归验证计划。

### REVIEW-S7-001：status service 的一次初始化契约尚未落实

- **阶段和文件**：S7，`services/mizu_status_service/mizu_status_service.c` 的 `mizu_status_service_init()`。
- **代码事实**：当前实现允许对已初始化 service 再次调用 init，并清空记录数组、替换记录数组绑定和 active count。
- **已确认设计**：status service 只允许一次成功初始化；已初始化对象再次 init 必须返回 `MIZU_STATUS_INVALID_STATE`，不得修改已有记录、记录数组绑定或服务状态。首次初始化失败后服务保持未初始化状态。
- **影响**：运行期重复初始化会清除当前错误，并可能把状态服务切换到另一块记录存储。
- **后续动作**：S7 使用与设计复核结束后，单独制定生产代码修复和回归验证计划。

### REVIEW-S8-001：menu 的一次初始化契约尚未落实

- **阶段和文件**：S8，`services/menu/menu.c` 的 `mizu_menu_init()`。
- **代码事实**：当前实现允许对已初始化 menu 再次调用 init，并重新绑定描述表、服务、step cache，重置导航状态和反馈，同时重新写入 step cache。
- **已确认设计**：menu 只允许一次成功初始化；已初始化对象再次 init 必须返回 `MIZU_STATUS_INVALID_STATE`，不得修改旧菜单状态、描述表绑定、服务绑定或 step cache。首次初始化失败后菜单保持未初始化状态。
- **影响**：运行期重复初始化会丢失导航、编辑草稿、feedback 和运行期步长状态，也可能切换到另一套菜单资源。
- **后续动作**：S8 使用与设计复核结束后，单独制定生产代码修复和回归验证计划。

### S8：mizu_menu 已确认

- menu 对象、描述表、文本、服务依赖和 step cache 均由 Composition Root/Application/Domain 提供；menu 不分配、不释放、不拥有业务数据或硬件。
- 一个 menu 实例对应一个交互/输出通道；不同屏幕或蓝牙会话使用独立 menu 实例和独立 step cache。
- root/group/item/display-page 描述在装配阶段固定，运行期不注册、删除或修改。
- 参数编辑期间只修改 menu 私有草稿；确认前重新读取真实参数，发现外部变化则报告冲突而不覆盖；只有 setter 成功才退出编辑并显示 applied。
- step cache 属于 menu owner/实例，不属于 parameter service；初始化复制默认步长，步长编辑只影响该 menu 实例。
- display page 只返回 page 元数据；实时数据由 Domain 或输出适配器查询和格式化，menu 不拥有实时数据、不依赖显示或通信协议。
- command 返回 BUSY 后 menu 不轮询、不阻塞，记录反馈并回到普通菜单状态。
- 原始按键、长按、编码器、蓝牙协议和输入适配全部位于 menu 外部；menu 只接收逻辑事件。
- 未发现除 `REVIEW-S8-001` 外的 S8 实现问题。

### S7：mizu_status_service 已确认

- service 只保存上层显式选择、当前仍需顶层输出的错误，不保存历史、时间、严重级别、计数或业务载荷。
- `source_id` 由 Application/Domain 固定定义；service 不预注册所有可能来源。
- records 是动态活动错误槽位表：新来源占用空槽，重复来源更新原槽，clear 回收槽位。
- `record_count` 表示允许同时保存的最大活动错误数，不表示来源总数；owner 根据故障模型和顶层输出需求静态确定该上限。
- 容量满时返回 `MIZU_STATUS_FULL`，不覆盖已有错误；系统不能承诺无限数量来源都能同时保存。
- `get_by_source()` 是稳定查询方式；`get_at()` 只按当前槽位遍历，不表示来源优先级。
- 记录数组由状态/诊断 owner 在 `.c` 内私有静态持有；service 不分配、不释放、不创建隐藏全局存储。
- 并发一致性、ISR 转交、错误恢复和业务处理由 owner/Application 保证；未发现除 `REVIEW-S7-001` 外的 S7 实现问题。

### S6：mizu_command_service 已确认

- command service 只借用静态命令表、名称、handler 和 context，不拥有业务动作状态。
- handler 只接收 context；命令参数调整走 parameter service，不在 command 中增加通用运行时参数。
- execute 同步调用 handler 一次，handler 状态原样返回；BUSY 只表示本次 handler 结果，command 不自动轮询、不保存异步活动状态。
- snapshot 只保存最近一次执行结果的 ID、状态、序号和有效标志，不替代 Domain 的异步动作状态机。
- handler 的阻塞、锁、并发、重入和业务状态由 owner/Application 保证，command service 不提供同步。
- 未发现除 `REVIEW-S6-001` 外的 S6 实现问题。

## 9. 已确认的阶段结论

### S2：mizu_fifo

- FIFO 对象和 storage 由 Services/communication 或其他明确的 owner 模块在 `.c` 文件内以 `static` 持有；业务调用方不直接接触 FIFO 对象、storage 或游标。
- owner 模块负责对外提供通信语义 API，并保证 FIFO storage、DMA 缓冲区、写入输入区和读取输出区不重叠；mizu_fifo 不做通用地址范围检测。
- FIFO 保持完整写入/完整读取语义，不提供 used/free/peek/reset 等额外接口。
- 并发、原子性、内存可见性、临界区和 RTOS 同步由实际使用者和平台边界负责；mizu_fifo 只规定单生产者/单消费者约束。
- storage 大小保留一个空槽，实际可用容量为 `storage_size - 1`；空、满、零长度和游标回绕语义保持不变。
